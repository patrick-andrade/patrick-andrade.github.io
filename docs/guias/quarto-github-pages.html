  • A leitura essencial cabe em cerca de 5 minutos; o restante é opcional.

Introdução: Quarto e GitHub Pages

Você escreve relatórios em um processador de texto e depois tenta “subir um site”?
- Rotina: exportar PDF, anexar em e-mail, e ainda não ter um endereço estável para apontar?

Este guia mostra o salto: uma pasta versionada no Git e um site estático gerado pelo Quarto, publicado no GitHub Pages. O HTML em docs/ é o produto; os arquivos .qmd e o _quarto.yml são a fonte.

1. Trate o site como pasta versionada e HTML estático

Recomendação - Trabalhe em uma pasta de projeto com Git. Escreva páginas em Quarto (.qmd). Publique o HTML gerado, não o arquivo de edição.

Por que / ganhos - O endereço público deixa de depender de anexo ou de pasta na nuvem. - O histórico fica no Git: você recupera um estado anterior sem site_final_v3. - Atualizar o site vira o mesmo ciclo de qualquer projeto versionado: editar, conferir, registrar, enviar.

Na prática - A pasta local é o lugar do trabalho. O GitHub guarda a cópia remota e o GitHub Pages serve o HTML. - Não transforme a Área de Trabalho nem a raiz de um disco em site. - Um repositório = um site (ou um projeto). Não misture trabalhos não relacionados na mesma raiz do Git.

Cuidado

O Git precisa existir nesta pasta — a raiz do site —, não na pasta agregadora que a contém. Commit e quarto render na pasta errada não publicam o que você editou.

2. No GitHub, o repositório chama usuario.github.io

Recomendação - Para o site de usuário do GitHub Pages, o nome do repositório no GitHub deve ser exatamente seu-usuario.github.io.

Por que / ganhos - Esse nome é o contrato da URL https://seu-usuario.github.io. Outro nome no remoto não vira site de usuário. - O nome da pasta no disco pode ser outro (por exemplo um prefixo local de ordem visual). O que o GitHub exige é o nome do repositório remoto.

Na prática - Crie o repositório público seu-usuario.github.io no GitHub (README inicial pode ficar desmarcado). - No disco, Set-Location até a pasta que é a raiz do .git desse site. - Confira o remoto: git remote -v deve apontar para https://github.com/seu-usuario/seu-usuario.github.io.git.

Nota

Prefixos locais (01-, 00-) servem para ordem no Explorador. Não os coloque no nome do repositório no GitHub nem na URL pública.

3. _quarto.yml com output-dir: docs

Recomendação - Declare o site como projeto Quarto do tipo website e grave a saída em docs/.

Por que / ganhos - O GitHub Pages, neste fluxo, publica a pasta /docs da branch main. Sem output-dir: docs, o HTML fica em outro lugar e o site não atualiza. - O _quarto.yml concentra título, URL, navbar e tema. Páginas novas entram na navegação de forma explícita.

Na prática

Núcleo mínimo (adapte nome, URL e itens do menu):

project:
  type: website
  output-dir: docs

lang: pt-BR

website:
  title: "Seu Nome"
  site-url: "https://seu-usuario.github.io"
  navbar:
    left:
      - text: "Início"
        href: index.qmd
      - text: "Sobre"
        href: sobre.qmd

format:
  html:
    theme: cosmo
    css: styles.css
    toc: true

O item que não pode faltar na primeira publicação:

output-dir: docs

4. preview → render → commit na raiz do Git → push → Pages em main /docs

Recomendação - Confira localmente, gere docs/, registre na raiz do repositório e só então envie. No GitHub: Pages a partir de main e da pasta /docs.

Por que / ganhos - quarto preview mostra o site sem gerar o pacote de publicação. - quarto render escreve o HTML que o GitHub Pages vai servir. Sem esse passo, o remoto fica com fonte nova e site antigo. - Commit fora da raiz do .git não entra no repositório que o Pages lê.

Na prática

Set-Location 'C:\caminho\do\seu-usuario.github.io'
quarto preview

Interrompa a prévia com Ctrl + C. Depois:

quarto render
git status
git add .
git commit -m "Mensagem clara do porquê."
git push

No GitHub, no repositório seu-usuario.github.io:

Settings → Pages → Build and deployment
Source: Deploy from a branch
Branch: main
Folder: /docs
Save

Aguarde alguns minutos e abra https://seu-usuario.github.io.

Cuidado

git add . inclui o que não está no .gitignore. Não envie .env, chaves nem relatórios de uma máquina específica. A pasta .quarto/ de cache local não deve ir para o remoto.

Primeira sessão: cinco passos

  1. Confirme git --version e quarto --version. Crie no GitHub o repositório seu-usuario.github.io (público, nome exato).
  2. Na pasta local que será a raiz do Git, crie o projeto (quarto create project website . se ainda não houver _quarto.yml) e defina output-dir: docs.
  3. Escreva pelo menos index.qmd e sobre.qmd, ligue-os na navbar, rode quarto preview e corrija o que aparecer.
  4. Rode quarto render. Confira se docs/ existe e se há docs/.nojekyll (o Quarto costuma criá-lo; se não, crie-o na raiz e renderize de novo).
  5. Na raiz do Git, git add, git commit com o porquê, git push. Configure Pages em main /docs e abra a URL pública.

Nota

Esta parte aprofunda quatro temas. Não é necessária para começar. Volte aqui quando for montar o esqueleto das páginas, ajustar estilo, diagnosticar uma URL vazia ou rotinizar atualizações.

Persona Adam Smith e esqueleto das páginas

Para tornar o exemplo concreto, use dados fictícios e substitua pelo seu usuário real:

Nome: Adam Smith
Área: Economia política e filosofia moral
Usuário GitHub: adam-smith
Repositório no GitHub: adam-smith.github.io
URL: https://adam-smith.github.io

Um esqueleto inicial cabe em poucas páginas. Não abra seção no menu sem conteúdo:

adam-smith.github.io/          # raiz do Git (o nome no disco pode diferir)
├── _quarto.yml
├── index.qmd
├── sobre.qmd
├── projetos.qmd
├── ensino.qmd
├── contato.qmd
├── styles.css
├── .nojekyll
├── README.md
└── docs/                      # gerada por quarto render; é o que o Pages serve

index.qmd (homepage) apresenta quem é o autor e o que o site oferece. sobre.qmd não precisa duplicar o currículo: uma minibio e áreas de interesse bastam. projetos.qmd só lista o que já tem página honesta (pergunta, dados, status). ensino.qmd descreve abordagem, não um ambiente virtual de aprendizagem. contato.qmd aponta canais que você de fato lê.

YAML ilustrativo da homepage:

---
title: "Adam Smith"
---

Este site reúne pesquisas, projetos e materiais de ensino em economia política.

## Áreas de interesse

- Divisão do trabalho
- Mercados e instituições
- Ensino de economia

Substitua adam-smith pelo seu usuário. O repositório no GitHub permanece seu-usuario.github.io, mesmo que a pasta local tenha outro nome.

.nojekyll e styles.css

O GitHub Pages, por padrão, pode tratar o repositório como projeto Jekyll. Um arquivo .nojekyll na raiz e em docs/ evita esse processamento. O Quarto costuma gerar docs/.nojekyll no render. Na raiz do projeto, touch .nojekyll (Git Bash) ou, no PowerShell:

New-Item -ItemType File -Name .nojekyll -ErrorAction SilentlyContinue

styles.css entra no _quarto.yml em css: styles.css. Comece mínimo; o tema (por exemplo Cosmo) já define o essencial:

body {
  line-height: 1.6;
}

.navbar-title {
  font-weight: 600;
}

Ajuste visual depois que a publicação estiver estável. Tema e CSS não substituem conteúdo.

Erros comuns

O site não aparece ou permanece na versão antiga. O Pages ainda está processando; o repositório não se chama usuario.github.io; a fonte não é main /docs; quarto render não foi rodado; docs/ não entrou no commit. Confira git status na raiz do Git e, se houver HTML novo, faça commit e push.

O menu aponta para página inexistente. O href no _quarto.yml não coincide com o nome do arquivo. projetos.qmd no YAML exige um arquivo exatamente com esse nome.

Commit na pasta errada. Se git status não lista os .qmd que você editou, você não está na raiz do .git do site. Suba de diretório até achar a pasta que contém .git e _quarto.yml.

Nada para commitar. nothing to commit, working tree clean significa que não há alteração desde o último commit — inclusive se você esqueceu o quarto render e só mudou o .qmd que já estava igual ao índice, ou se o HTML gerado está no .gitignore.

O GitHub pede autenticação no push. Conclua o login no navegador ou no Git Credential Manager. O guia GitHub na Prática cobre gh auth login.

Fluxo depois da publicação

Depois que a URL pública responder, o ciclo é o mesmo:

1. Editar os .qmd na raiz do Git do site
2. quarto preview (opcional)
3. quarto render
4. git status na raiz do repositório
5. git add / git commit / git push
6. Conferir a URL publicada

No PowerShell, um comando por linha:

Set-Location 'C:\caminho\do\repositorio-do-site'
quarto render
git status
git add .
git commit -m "Atualiza conteúdo do site."
git push

Não rode git init de novo em um repositório que já tem .git. Não publique seção nova no menu só para ocupar lugar: página vazia reduz credibilidade.
