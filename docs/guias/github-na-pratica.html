GitHub na Prática

Salto do arquivo final_v2 para Git no disco e GitHub como cópia remota, com comandos no Windows PowerShell.

Versão: 0.1.2
Última revisão das fontes: 18 de agosto de 2026

  • A leitura essencial cabe em cerca de 5 minutos; o restante é opcional.
  • Os comandos valem no Windows PowerShell 5.1 (o terminal padrão do Windows 10/11). Não use && entre comandos: nessa versão isso falha. Escreva um comando por linha.
  • O guia pressupõe git (e, para usar o GitHub pelo terminal, gh) instalados e disponíveis no PATH.

Introdução: GitHub na prática

Você guarda versões de um relatório com nomes do tipo final_v2_corrigido.docx?

  • Rotina: copiar a pasta, mandar por e-mail, e depois não saber qual arquivo é o certo?

Este guia descreve o salto para Git (histórico no disco) e GitHub (cópia remota e ponto de encontro). A pasta local continua sendo o lugar do trabalho; o remoto é backup e colaboração, não um substituto do Explorador de Arquivos.

1. Separe Git de GitHub

Recomendação

  • Trate Git como o histórico na pasta do projeto e GitHub como o serviço que guarda uma cópia desse histórico e permite trabalhar com outras pessoas.

Por que / ganhos

  • Git responde “o que mudou, quando e por quê?” sem duplicar arquivos.
  • GitHub responde “onde está a cópia canônica remota?” e “como outra pessoa puxa ou envia mudanças?”.

Na prática

  • Git vive no computador: a pasta do projeto ganha um diretório .git (não edite esse diretório à mão).
  • GitHub vive na web: repositórios, Issues, pull requests. Você autentica uma vez e usa push / pull no PowerShell.
  • A pasta do trabalho continua no disco. Não transforme a Área de Trabalho nem a raiz de um disco em repositório.
Cuidado

Não rode git init em uma pasta agregadora — a Área de Trabalho, a raiz de um disco ou uma pasta que apenas reúne vários projetos. O repositório vive na pasta de um projeto. Cada projeto ganha o próprio repositório, quando chegar a hora.

2. Use o remoto como histórico, backup e encontro

Recomendação

  • Versionar no Git e publicar no GitHub quando o trabalho precisar de histórico estável, cópia fora da máquina ou colaboração.

Por que / ganhos

  • Você recupera um estado anterior sem procurar final_v3.
  • A cópia remota sobrevive a troca de computador, OneDrive fora de sincronia ou disco cheio.
  • Outra pessoa clona o mesmo projeto em vez de receber um ZIP desatualizado.
  • Rascunhos podem ficar em repositório privado; a publicação pública é uma decisão posterior.

Na prática

  • Um repositório = uma pasta de projeto, não um amontoado de trabalhos não relacionados.
  • commit registra um recorte local com uma mensagem do porquê.
  • push envia o que já está commitado; pull traz o que está no remoto antes de você continuar.

3. Estudantes: GitHub Pro pelo Student Pack

Recomendação

  • Se você é estudante, verifique-se no GitHub Student Developer Pack. Enquanto a verificação valer, o Pack inclui GitHub Pro.

Por que / ganhos

  • Repositórios privados ilimitados e recursos avançados de repositório (insights, ferramentas de colaboração) sem pagar o plano Pro.
  • O Pack é um conjunto de ofertas; o que conta aqui é o Pro na conta GitHub. Demais parceiros são opcionais.

Na prática

  • Acesse education.github.com/pack, use a conta GitHub e envie comprovante de matrícula (e-mail institucional costuma acelerar).
  • A elegibilidade é para estudantes verificados (em geral a partir de 13 anos). Docentes, pesquisadores e demais vínculos acadêmicos não entram no Student Pack; usam o GitHub Education, com benefícios distintos.
  • Ofertas de parceiros mudam. Confira a página oficial; não dependa de Copilot nem de um brinde específico como se fossem permanentes.
Nota

O Pro do Pack vale enquanto a verificação de estudante estiver ativa. Depois da formatura, a conta volta ao plano gratuito salvo se você assinar.

4. Comandos no PowerShell, na pasta certa

Recomendação

  • Rode Git dentro da pasta do projeto. Um comando por linha. Coloque caminhos com espaço entre aspas.

Por que / ganhos

  • O Windows PowerShell 5.1 não encadeia com &&. Linhas separadas evitam erro e deixam claro o que falhou.
  • Set-Location (ou o alias cd) garante que init, pull e push atuem no repositório certo.

Na prática

Confira as ferramentas (as duas devem responder):

git --version
gh --version

Autentique o GitHub CLI uma vez (abre o navegador; o Git Credential Manager passa a guardar a credencial):

gh auth login

Entre na pasta do projeto:

Set-Location 'C:\caminho\do\projeto'
git status

Repositório novo, ainda só no disco:

git init
git add .
git commit -m "Mensagem clara do porquê."
git branch -M main

Ligue o remoto e envie a primeira versão (crie o repositório vazio no GitHub antes, ou use gh repo create no Saiba mais):

git remote add origin https://github.com/org/repo.git
git push -u origin main

Ciclo diário, sempre na pasta do projeto:

git status
git add .
git commit -m "Mensagem clara do porquê."
git pull
git push

Copiar um repositório que já existe:

git clone https://github.com/org/repo.git
Cuidado

git add . inclui tudo que não está no .gitignore. Não commite .env, chaves, credentials*.json nem relatórios de uma máquina específica.

Primeira sessão: cinco passos

  1. Confirme git --version e, se for usar o GitHub pelo terminal, gh auth login.
  2. Set-Location na pasta do projeto (não em uma pasta agregadora).
  3. git init (ou git clone se o remoto já existir), depois git status.
  4. Primeiro recorte: git add, git commit com o porquê, git branch -M main.
  5. git remote add origin ... (se ainda não houver), git push -u origin main. No dia seguinte: git pull antes de continuar, git push depois do commit.

O objetivo do commit é o porquê da mudança, não a lista de arquivos. O Git já guarda quais arquivos entraram.

Saiba mais — quando o uso já estiver andando

Nota

Esta parte aprofunda cinco temas. Não é necessária para começar. Volte aqui quando .gitignore, identidade, fetch ou a criação do repositório pelo terminal aparecerem no seu trabalho.

.gitignore e o que não deve ir para o remoto

Crie um arquivo .gitignore na raiz do repositório com padrões, um por linha: .env, .venv/, reports/, *.pem. O que já foi commitado não some só de entrar no ignore; precisa ser retirado do índice com cuidado. Segredos que vazaram exigem troca da credencial, não só um commit novo.

git fetch versus git pull

git fetch só atualiza o que o Git sabe do remoto, sem misturar na sua pasta. git pull busca e tenta incorporar na branch atual. No dia a dia, git pull antes de git push costuma bastar. Se houver conflito, o Git interrompe e pede para você resolver os arquivos marcados.

Criar o repositório com gh

Com gh auth login já feito, na pasta do projeto:

gh repo create nome-do-repo --private --source . --remote origin --push

--private mantém o rascunho fora do público. Troque para --public só quando a publicação for deliberada. --source . usa a pasta atual; --push envia o que já estiver commitado.

Identidade: nome e e-mail nos commits

O Git recusa commit sem identidade. No PowerShell, neste repositório (sem alterar a configuração global da máquina, a menos que você queira):

git config user.name "Seu nome"
git config user.email "voce@instituicao.br"

Use o e-mail da conta GitHub (ou o e-mail privado que o GitHub fornece nas configurações) para os commits aparecerem ligados ao seu perfil.

OneDrive e arquivos sob demanda

Se o projeto estiver no OneDrive, marque a pasta como Sempre manter neste dispositivo antes de clone, pull ou push. Arquivo só na nuvem vira erro opaco no Git.
